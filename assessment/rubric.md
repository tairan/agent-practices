# 能力与阶段验收 Rubric

## 能力域

| ID | 能力域 | 核心问题 |
|---|---|---|
| `model` | 模型行为与能力适配 | 如何发现能力边界、漂移并降级 |
| `prompt-context` | Prompt 与 Context Engineering | 如何表达契约并选择本次可见信息 |
| `tool-loop` | Tool、Workflow 与 Loop Engineering | 如何安全执行动作、推进状态并稳定停止 |
| `knowledge-data` | 检索、记忆与数据生命周期 | 如何保证证据、权限、时效、删除和 provenance |
| `evaluation` | 评测与实验设计 | 如何证明收益、识别退化并避免污染 |
| `security` | 安全、身份与数据治理 | 如何限制主体、权限、数据和不可信输入的影响 |
| `reliability` | 分布式运行与生产运营 | 如何处理重试、幂等、故障、容量、发布和事故 |
| `interop` | 协议与企业集成 | 如何实现和验证跨系统契约 |
| `human-product` | 人机交互与产品判断 | 何时提问、执行、解释、审批、撤销或不用 Agent |
| `architecture` | 架构、取舍与技术沟通 | 如何比较方案、控制复杂度并解释演进 |

## 通用等级

| 等级 | 定义 | 必须展示的行为 | 不足以证明该等级的材料 |
|---|---|---|---|
| `L0` | 识别 | 能指出机制存在 | 只列术语 |
| `L1` | 解释 | 能解释边界、假设和典型失败 | 复述文档但无法定位代码边界 |
| `L2` | 实现 | 从零实现最小闭环并覆盖已知失败 | 只运行框架样例或成功 demo |
| `L3` | 诊断与设计 | 处理未知故障，比较替代方案并用数据取舍 | 只修复自己预先编写的案例 |
| `L4` | 运营与演进 | 在负载、漂移、攻击或事故下止损、恢复和改进 | 只提交设计文档或模拟成功路径 |

项目只能提供一个或多个能力域的 evidence，不能自动授予等级。同一机制必须通过至少一次未知输入、故障或设计约束的迁移验证，才能从 L2 进入 L3。L4 必须包含真实运行或符合 [`blind-task-protocol.md`](blind-task-protocol.md) 的未知故障运营演练。

## 能力域行为锚点

| 能力域 | L2 | L3 | L4 |
|---|---|---|---|
| `model` | 实现最小适配器并分类停止、拒答和错误 | 用 conformance 和回归诊断未知 provider 差异 | 管理漂移、canary、降级和回滚 |
| `prompt-context` | 实现版本化 prompt 与显式 context builder | 诊断未知注入、冲突或预算问题并完成消融 | 在数据与模型变化下运营策略和回归门禁 |
| `tool-loop` | 实现校验边界、预算、取消和稳定终止 | 诊断未知振荡、错误动作或副作用问题 | 在真实或等价事故中止损、恢复并改进闭环 |
| `knowledge-data` | 实现 provenance、ACL、TTL 和删除路径 | 诊断未知陈旧、冲突、投毒或删除传播问题 | 运营索引迁移、审计和数据生命周期 |
| `evaluation` | 建立 baseline、数据集和确定性指标 | 设计盲测、统计分析和消融 | 运营线上评测、漂移检测和发布门禁 |
| `security` | 实现最小权限、授权和攻击测试 | 审查未知攻击路径并校准影响 | 在攻击演练或事故中止损、保全审计并演进控制 |
| `reliability` | 实现超时、有限重试、幂等和恢复 | 诊断未知跨模块或分布式故障 | 对 SLO、容量、发布和事故结果负责 |
| `interop` | 实现锁定版本的最小协议 | 定位未知跨实现兼容问题 | 运营版本迁移、兼容窗口和回滚 |
| `human-product` | 实现澄清、影响预览、审批和纠错 | 用研究或数据调整交互取舍 | 运营接管率、审批疲劳和高风险行为策略 |
| `architecture` | 解释边界并完成 baseline 比较 | 对未知约束完成方案取舍和 ADR | 推动生产化、build-vs-buy 和演进路线 |

## Foundation Gate

目标是 `model`、`prompt-context` 和 `tool-loop` 达到 L2，并具备基本评测能力。必须覆盖：

- 模型随机性、上下文、停止原因和能力差异。
- 稳定 Prompt ID/版本、变量边界、可信指令与不可信数据分隔、候选选择或单候选理由及版本回归。
- 结构化输出与确定性校验。
- 工具 schema、参数校验和错误边界。
- 显式 Agent loop、预算、取消和稳定终止。
- context builder、来源标记和 token 预算。
- 模型、工具、网络和协议错误恢复。
- 非 Agent baseline 与确定性评测。

通过条件：独立实现最小闭环，并在未提前公开的失败样本上完成诊断和修复说明；未知样本必须至少覆盖 Prompt 指令冲突、变量注入或输出不合规中的一种。

## Systems Gate

目标是组合单点机制并形成可复核的系统级 L3 evidence。通过门禁时，`tool-loop`、`evaluation`、`security`、`reliability` 和 `architecture` 必须达到 L3；此外 `knowledge-data` 或 `interop` 至少一个达到 L3。

同一个集成盲测可以支持多个能力域，但评审记录必须逐域指出独立的观察事实、诊断行为和设计取舍，不能用一次任务通过自动推断全部等级。必须覆盖：

- 至少一种持久化、恢复或长任务机制。
- 至少一种跨进程协议或企业连接器。
- 授权、工具权限、prompt injection 风险和数据边界。
- 观测、回归评测、容量预算和故障注入。
- 对多 Agent、RAG 或动态执行是否必要的 ADR。
- 真实模型 provider conformance。无凭据时可以标记 `deferred` 并继续后续学习，但 Systems Gate 只能记为 provisional，不得标记通过或声称真实兼容已验证；补齐 conformance evidence 后才能正式通过。

通过条件：完成一次跨模块故障定位，并证明失败不会产生越权、失控重试或重复不可逆副作用。

## Specialization Gate

学习者根据岗位选择企业授权、多 Agent、检索与记忆、分布式运行、协议、浏览器、多模态或评测工程。未选择方向必须说明适用场景和风险，但不要求完成全部项目。

通过条件：所选方向至少达到 L3，并完成一次跨能力域集成，例如“检索 + ACL”“Subagent + 缩减权限”或“浏览器 + 审批绑定”。

## Senior Gate

必须同时满足：

1. `model`、`prompt-context`、`tool-loop`、`knowledge-data`、`interop`、`human-product` 和 `architecture` 不低于 L3。
2. `evaluation`、`security` 和 `reliability` 不低于 L4。
3. 除 `evaluation`、`security` 和 `reliability` 外，至少两个与目标岗位相关的能力域达到 L4。
4. 完成至少两个综合项目，其中一个覆盖生产运行与事故处理。
5. 综合项目包含非 Agent baseline，并以统计上可解释的结果证明或否定 Agent 收益。
6. 完成未知代码或 trace 的限时故障诊断，以及未知攻击或越权场景的安全审查。
7. 完成模型或 prompt 漂移后的回归、canary 和 rollback 演练。
8. 完成 build-vs-buy ADR，比较自研机制与框架或托管 runtime。
9. 通过架构答辩，解释不变量、失败模式、替代方案、成本和演进路线。
10. 提供真实运行 evidence，或在受控环境完成包含未知故障的等价运营演练。
11. 能指出不应使用 Agent、多 Agent、RAG、长期记忆、浏览器操作或动态插件的场景。
12. 能在质量、延迟、成本、安全、隐私和可维护性之间给出有 evidence 的取舍。

## Capstone 评分

| 维度 | 分值 |
|---|---:|
| 正确性与任务效果 | 15 |
| 架构边界与可维护性 | 10 |
| 评测、baseline 与实验质量 | 15 |
| 安全、身份、隐私与数据治理 | 15 |
| 可靠性、幂等与故障恢复 | 15 |
| 可观测性、SLO 与运营能力 | 10 |
| 人机交互与产品判断 | 10 |
| 成本、延迟与容量 | 5 |
| 文档、ADR 与答辩 | 5 |

每个维度只能依据下表选择 `0%`、`40%`、`60%`、`80%` 或 `100%` 档，再乘以该维度分值。处于两档之间时取较低档，不得凭整体印象插值。

| 维度 | 40% | 60% | 80% | 100% |
|---|---|---|---|---|
| 正确性与任务效果 | 有成功 demo，但样本或预期不完整 | 满足契约并覆盖主要已知失败 | 未知输入下仍有量化效果和失败分类 | 漂移或复杂未知约束下保持效果并改进指标 |
| 架构边界与可维护性 | 能运行但边界耦合或隐式 | 核心接口、状态和责任边界明确 | 用 ADR 比较替代方案并完成迁移 | 演进、兼容和 rollback 经实证验证 |
| 评测、baseline 与实验质量 | 有指标但无可靠 baseline 或隔离 | baseline、数据集、评分器和预算可复现 | 有盲测、统计、消融和污染检查 | 线上或等价漂移门禁持续运营 |
| 安全、身份、隐私与数据治理 | 有零散校验但威胁边界不全 | 满足最小权限、数据治理和已知攻击测试 | 未知攻击下保持不变量并审计完整 | 攻击演练后完成控制演进和复验 |
| 可靠性、幂等与故障恢复 | 有重试但缺少幂等或恢复证明 | 已知故障下有界重试、幂等和恢复 | 未知跨模块故障下完成止损和恢复 | 真实或等价事故驱动机制改进 |
| 可观测性、SLO 与运营能力 | 有日志但无法端到端关联 | SLI/SLO、关联 ID、告警和 runbook 完整 | 未知故障中通过观测定位并满足恢复目标 | 长期运营数据驱动容量和告警演进 |
| 人机交互与产品判断 | 能审批但影响表达或纠错不足 | 澄清、影响预览、拒绝、纠错和撤销完整 | 用数据处理接管率和审批疲劳 | 在高风险场景持续优化且不转嫁判断 |
| 成本、延迟与容量 | 仅估算或单次测量 | 按契约测量 p50/p95、成本和容量上限 | 负载与退化条件下解释取舍 | 通过路由、降级或架构变化持续优化 |
| 文档、ADR 与答辩 | 有运行说明但证据不可追溯 | 文档、ADR 和 evidence index 可复核 | 能回答未知约束和反方案质询 | 决策、事故和演进形成可复用组织知识 |

`0%` 表示完全缺失、证据不可信或触发该维度的直接不通过条件。低于 `40%` 的部分实现统一按 `0%` 计。

严重凭据泄露、跨租户访问、不可控副作用、伪造授权、评测污染、隐瞒失败数据或无法恢复的数据破坏直接不通过。

资深候选人的每个 Capstone 必须至少 80 分，任一维度不得低于该维度满分的 60%，且 Capstone 分数不得替代能力矩阵。
